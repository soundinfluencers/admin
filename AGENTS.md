# AGENTS.md — SoundInfluencers Admin

Инструкции для работы AI-агентов в репозитории административного приложения. Это правила выполнения задач и подтверждённые ограничения, а не полное описание архитектуры или отчёт о готовности функций.

## 1. Режим работы и границы задачи

- Общайся с пользователем на русском языке. Имена в коде и тексты интерфейса сохраняй в принятом в проекте стиле.
- Выполняй конкретно поставленную задачу. Если запрошено обсуждение, аудит или план, не переходи к редактированию кода без соответствующего указания.
- Если реализация уже поручена и scope определён, выполняй её без повторного запроса разрешения на каждый файл или небольшой шаг.
- Перед правками кратко объясни, что изменишь. Существенные изменения бизнес-логики, API-контрактов или архитектуры сначала обсуди, если они не входят в согласованную задачу.
- Предпочитай минимальный связный diff. Не включай попутные рефакторинги, форматирование всего файла, переименования и исправления несвязанных проблем.
- Обнаруженные проблемы вне scope перечисляй отдельно. Не расширяй задачу самостоятельно.
- Не используй субагентов без явного запроса пользователя.

## 2. Начало работы и Git

- Прочитай существующие инструкции, применимые к изменяемым файлам. Отсутствие дополнительной документации само по себе не блокирует задачу и не требует её создания.
- Проверь текущую ветку, `git status` и относящиеся к задаче локальные изменения. Не предполагай, что рабочее дерево чистое или что нужно переключить ветку.
- Сохраняй существующие пользовательские изменения. Не откатывай, не удаляй и не перезаписывай их ради удобства выполнения задачи.
- Commit, push, merge, переключение ветки и deploy выполняй только по прямому указанию пользователя. Разрешение изменить код не означает разрешение публиковать его.
- Для поиска используй `rg` / `rg --files`. Определи реальные пути по репозиторию; не придумывай структуру каталогов.
- При наличии старой и новой реализации сначала установи, какая входит в scope. Для Campaign Management V2 старую реализацию не используй как источник обязательных бизнес-правил и не изменяй без отдельной задачи.

## 3. Стек и существующие соглашения

Основной стек админки: React, TypeScript, Vite, SCSS Modules, Zustand с persist, TanStack Query v5, TanStack Table, Radix UI, React Hook Form и Zod.

- Точные версии, package manager, команды и архитектурные соглашения проверяй по актуальным файлам проекта.
- Используй существующие shared-компоненты, API-клиент, типы и query-key factories. Перед созданием нового решения проверь ближайшие аналогичные реализации.
- Следуй существующему разделению на entities, features, widgets и pages. Не перестраивай слои ради локальной правки.
- Для новых форм ориентируйся на принятый подход RHF + Zod; не переписывай ради унификации уже работающие небольшие контролы.
- Не добавляй зависимости и не обновляй lockfile без необходимости, обусловленной задачей.
- Не обходи проверки типов через `any`, необоснованные assertions или отключение диагностики.
- В показанных действиях Campaign Management store используются immutable updates. Сохраняй этот подход; не внедряй Immer в рамках локальной задачи.

## 4. API, серверные данные и ошибки

- Опирайся на актуальные типы, предоставленный Swagger и подтверждённые ответы. Не выдумывай endpoint, DTO, response или значение идентификатора.
- Не подменяй идентификаторы в API-параметрах только из-за похожих названий. Проверяй смысл каждого параметра.
- Используй принятый способ извлечения полезных данных из API-обёртки. Для endpoint без тела ответа не придумывай возвращаемые данные.
- Ошибки запросов глобально обрабатываются interceptor. Не добавляй дублирующие error toast без отдельной необходимости. Не подавляй ошибку так, чтобы операция выглядела успешной.
- Сохраняй существующие pending-состояния, запрет повторных кликов и success toast. Не добавляй автоматические повторы мутаций без понимания их последствий и идемпотентности.
- Локальное изменение draft и подтверждённая сервером операция — разные события. Не сообщай о сохранении на сервере только на основании изменения Zustand или localStorage.
- Не выполняй изменяющие запросы к production ради проверки. Тестовые данные используй в локальной проверке либо в явно указанном пользователем тестовом окружении.

## 5. Campaign Management V2: идентичность размещений

Правила этого и следующих двух разделов относятся именно к Campaign Management V2, а не ко всем сущностям админки.

- Один социальный аккаунт может присутствовать в одной кампании несколько раз. Каждый элемент `campaign.addedAccounts` — отдельное размещение.
- `socialAccountId` идентифицирует социальный аккаунт и может повторяться внутри кампании.
- `addedAccountsId` идентифицирует конкретное размещение. Используй его для выбора, поиска, обновления, удаления, ключей компонентов и идентичности строк, когда действие относится к размещению.
- Передавай ID размещения последовательно через callbacks, props, хуки и store. Название аргумента должно соответствовать значению: не называй `addedAccountsId` параметром `socialAccountId`.
- Не выполняй глобальную замену поля `socialAccountId`: оно остаётся частью модели и используется там, где нужен сам социальный аккаунт.
- Не используй `socialAccountId`, индекс массива или случайный ID как fallback для отсутствующего `addedAccountsId`. Если реальный путь не предоставляет ID размещения, опиши проблему контракта.
- В Mark as Paid параметр `promoId` соответствует `addedAccountsId`.
- `campaignContentItemId`, `descriptionId` и `additionalBriefId` относятся к контенту. Не заменяй их ID размещения.
- Общий контент может использоваться несколькими размещениями. Его редактирование и удаление должны сохранять существующую семантику для всех связанных размещений. Не создавай индивидуальные копии и не меняй правила fallback без отдельной задачи.
- Не меняй агрегации, Reach, группировку или число размещений и не добавляй дедупликацию по `socialAccountId` в рамках исправления идентификации.

## 6. Campaign Management V2: права редактирования

Поле `canEdit` из ответа считается legacy и не используется для определения разрешений. Сохраняй существующие проверки актуального контекста draft.

| Действие | Under Review (`under_review`) | Distributing (`distributing`) | Completed (`completed`) |
| --- | --- | --- | --- |
| Название и Content Editor | Редактирование | Редактирование | Только просмотр |
| Добавление и удаление размещений | Разрешено | Разрешено | Запрещено |
| Цена | Редактирование | Редактирование | Только просмотр |
| Смена валюты | При наличии `pricesByCurrency` | При наличии `pricesByCurrency` | Запрещена |
| Редактируемые метрики таблицы | Заблокированы | Разрешены существующие поля | Заблокированы |
| Mark as Paid | Заблокирован | Доступен для неоплаченного промо | Заблокирован |
| Изменение Post Link / Screenshot | Заблокировано | Разрешено | Заблокировано |
| Открытие существующих ссылок и скриншотов | Доступно | Доступно | Доступно |
| Отправка сообщений | Заблокирована | Допустима с отдельными бизнес-правилами | Заблокирована |
| Show/hide бюджета и CPM/result | Доступно | Доступно | Доступно локально |
| Reset / Save в интерфейсе | Отображаются | Отображаются | Скрыты |

- Матрица описывает правила доступа, но не утверждает, что все перечисленные функции уже реализованы. Save и отправку сообщений подключай только в рамках соответствующей задачи и согласованных контрактов.
- В Completed сохраняй навигацию, переключение аккаунтов, чтение и копирование текста. Не блокируй весь контейнер через `pointer-events: none` или аналогичный общий запрет взаимодействия.
- Различай выбор для просмотра и выбор, меняющий привязку контента. Второй в Completed запрещён.
- Для текстовых полей режима просмотра используй `readOnly`, где это соответствует существующему компоненту; для изменяющих селекторов и кнопок — предусмотренный `disabled` или условное скрытие.
- Проверки пользовательского редактирования сохраняй и в UI, и в соответствующих действиях store. Не блокируй общим запретом гидратацию, очистку draft и применение подтверждённых серверных результатов.
- Proposal (`proposal`): таблицы аккаунтов нет; Content Editor редактируемый, добавление аккаунтов доступно, Advanced Insight служит для просмотра.
- Top Country и Genres в Advanced Insight не редактируются. CPM не является редактируемой метрикой таблицы.

## 7. Campaign Management V2: draft и совместимость

- Данные сервера и редактируемый локальный draft имеют разные роли. Не заменяй draft целиком после мутации или фонового GET без понимания влияния на несохранённые изменения.
- Update Insights: после разрешения dirty draft блокируй все изменения с начала подготовительного Save/Discard до завершения PATCH и GET. Подтверждённый GET полностью принимается в query cache, baseline и draft через механизм серверного снимка; изменение состава размещений допустимо. При ошибке синхронизации сохраняй блокировку и повторяй только GET.
- При асинхронном применении результата сохраняй проверки принадлежности ответа текущей кампании и целевой записи.
- Не считай инвалидацию query сама по себе безопасной для редактора: проверь, как полученный ответ применяется к draft.
- Архитектура baseline, dirty state, фоновой синхронизации, persist, Save и навигации требует отдельной задачи. Не реализуй её попутно и не считай окончательно готовой на основании наличия функций с похожими названиями.
- Старые кампании могут не иметь `pricesByCurrency`. В этом случае используй `price` и `displayCurrency`, блокируй смену валюты и при редактировании цены не создавай неполную карту валют.
- При наличии `pricesByCurrency` сохраняй согласованное обновление цены и соответствующего значения карты валют.
- Mark as Paid — отдельная серверная операция без подтверждающей модалки и без возможности отмены через повторный клик. Применяй подтверждённые `closePromo` и `statusLabel` из ответа к нужному размещению, сохраняя остальные локальные поля.
- No-op для результата Paid допустим, только если совпадают оба поля: `closePromo` и `statusLabel`.

## 8. Проверки и завершение задачи

- Команды проверки находи в `package.json`, конфигурации TypeScript, lockfile и существующей документации. Не придумывай npm scripts и не меняй конфигурацию ради прохождения проверки.
- Выполняй проверки, соответствующие изменению. Для сквозных изменений TS/TSX проверь типы и предусмотренную проектом сборку. Успешная Vite-сборка сама по себе не заменяет проверку типов, если она не входит в build script.
- Для изменений идентификации проверь две записи с одинаковым `socialAccountId` и разными `addedAccountsId`: независимый выбор, изменение и удаление. Используй минимальные синтетические данные, без production payload и контактов.
- Сохраняй поведение общих сущностей и ограничения статусов. Не ограничивай такую проверку единственной записью без дублей.
- Используй существующую тестовую инфраструктуру; не добавляй новый стек ради небольшой задачи. Не создавай бессодержательные тесты, повторяющие реализацию.
- При ошибке проверки отделяй регрессию от ранее существующей проблемы. Не исправляй несвязанные ошибки автоматически и не утверждай, что проверка прошла, если она не запускалась или завершилась ошибкой.
- Перед завершением просмотри diff на случайные правки и оставшиеся несогласованные вызовы.
- В отчёте кратко укажи: что изменено и зачем, какие проверки выполнены, их результат и что осталось проверить вручную. Отдельно отмечай результаты, подтверждённые пользователем, и собственные проверки.
